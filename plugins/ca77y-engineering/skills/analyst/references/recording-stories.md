# Recording and refining stories

Read immediately before creating or updating board cards. BOARD's shape and authority win; never invent fields, status values, endpoints, or a tracker.

Re-query through search by subsystem/outcome, including completed and parked work. Recheck duplicates, dependencies, and shared file/function regions for each card. Refresh counts from that search. Where overlaps exist, cross-link or record coordination on both sides only with declared update authority; otherwise report the reserved correction. State unavailable query coverage rather than calling it reconciled.

Use the native card shape and initial status. Include a stable identity, action-verb title, one type by central outcome, priority when known, goal/background, scope, source links, dependencies, and individually verifiable acceptance criteria (one behavior per line). Map types onto the board vocabulary; only bug, feature, and improvement are implementation-ready. Research and support proposals need refinement before lead delivery. Preserve board format quirks without propagating them to other projects.

One story is one card/PR; use linked stories for genuine prerequisites, not subtasks. Link research instead of pasting it. A deployed-state claim needs repository deployment evidence or an explicit unverified-from-repo label. If required semantics have no native field, use a documented convention or report the chosen representation and its limits.

When refining an existing card, read it and linked stories first. Preserve its identity and authorized scope; report significant changes. Never transition cards. If creation or update is unavailable, return the shaped proposal and needed corrections instead of writing elsewhere.
