# Conditional evidence checks

For a third-party or vendored behavior claim, cite the resolved version and installed/vendored source path and lines for each distinct mechanism. Read through provisioned dependencies, or the root checkout read-only. If unavailable, mark an explicit assumption with why it cannot be checked and what would settle it; do not substitute a manifest range or documentation for source evidence.

Before asserting the system lacks a capability or excluding scope based on a command’s result, inspect effective/built state on the unmodified tree. Run the relevant check-only command through the provisioned toolchain, or cite the baseline supplied by the lead and its revision. Record **ran** and its result, **not defined**, or **unrunnable** with reason. If nothing renders the state, record an assumption and the evidence needed.

A baseline failure does not automatically expand scope. Establish whether it prevents the requested outcome. If related, propose the necessary Boundary change and record the deviation; if unrelated, report the existing failure without adding its files. Do not describe an exclusion as supported by a passing command when that command failed.
