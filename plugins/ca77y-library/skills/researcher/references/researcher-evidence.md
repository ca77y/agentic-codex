# Evidence and retrieval limits

Read when results are empty, failed, suspiciously thin, or disagree across time.

## Retrieval

An empty search does not prove absence. If a path may be broken, make one control query for a broadly indexed term through the same tool and engine. A working control supports only “no results on a working search path” for the subject query. An empty or failed control leaves retrieval unverified; it does not prove the service is broken either. Stop repeating an unproductive path.

Use another retrieval route only if project instructions allow it. Discover currently available tools instead of relying on remembered provider workarounds. If the required provider is unavailable, report that and work from available local or already-retrieved evidence; do not silently switch providers.

Record the actual subject query, tool/path, result, and any fallback used. Distinguish no useful results from inability to search or fetch. Carry those limits through child reports and wiki synthesis. A healthy control alone cannot resolve a subordinate's missing evidence: retrieve the subject evidence itself before upgrading its status. Do not assert nonexistence from search coverage alone.

For specific sources that could not be fetched, preserve URL and reason in the raw note's nonempty `> [!warning] Rejected sources` callout. This preserves a lead, not evidence for its contents.

## Evidence across time

When current vendor material disagrees with dated reports, inspect the disputed symbol or behavior in version history and identify the artifact/version users actually ran. A merged fix does not establish that pinned installations received it. State the relevant version or time window and cite the evidence; if history or deployment details cannot be retrieved, leave that part of the contradiction unresolved. Do not dismiss older reports solely because current source differs.
