# Orchestrator ledgers

## Outcome and scope

Restore the user's requested mandatory ledger for every orchestrator in both plugins, including templates, subagent IDs, and ongoing progress. This covers engineering `shape`, `deliver`, `bootstrap`, `install-subagents` and library `ask`, `research`, `bootstrap`, `install-subagents`. Custom agents are isolated leaves; ledger ownership belongs to the invoking main agent. This is a local documentation/skill change; no release, installation, commit, or publication is requested.

## Contract

Every entry point opens or creates one durable Markdown ledger before production or delegation, including trivial and answer-only work. Reuse that ledger across entry points within the same prompt-to-resolution run. A separate later user request uses a new run ledger and attempt count, even for the same PR or artifact; prior ledgers remain context. The orchestrator is its sole writer; leaves return progress and evidence for integration. Initial context reading and ledger/spec preparation do not require recursive specification gates.

Discover existing state before creating a ledger: follow any supplied ledger path or spec/task/PR reference, then search the declared/default project ledger directory (or the personal directory for projectless work) for the same initiating request/run, project identity, outcome and acceptance source. A PR or artifact match alone does not identify the same run. Do not decide identity by entry-point name or error text. Record project identity and source checkout separately so a worktree change can match the same outcome. If records conflict, history is incomplete, or ownership cannot be resolved, return the recovery gap before further production. A different task must not claim an active owner's ledger: obtain an explicit handoff/release from that owner or the user. Before transfer, the outgoing owner saves current state and the destination/next owner; the incoming owner confirms the previous owner is no longer writing, records the transfer, and then resumes sole ownership. A resumed current task retains ownership. Record available task/owner handles honestly; do not invent missing runtime IDs.

Use the project's declared ledger location, otherwise `docs/ledgers/<run-id>.md` under the project root. For work without a project use `${CODEX_HOME:-~/.codex}/ledgers/<run-id>.md`. Generate a unique stable run ID when none is available; record the absolute ledger path. Never write run state into installed plugin source/cache, the research library, or disposable scratch. Keep the ledger through completion; carry it to the destination before a checkout/task handoff. This permits local workflow bookkeeping only, not library mutations, commits, or external writes. If persistence is explicitly forbidden or unavailable, return the ledger in the conversation and the unmet persistence condition; do not silently continue a workflow requiring a durable ledger.

Each plugin bundles an independently usable template and shared ledger procedure, owned by `deliver` for engineering and `research` for library; all other entry points link relatively within their own plugin. Essential ownership and update requirements remain visible in every entry point. A run without subagents or failures records `none`; it still uses the ledger.

The ledger records the initiating request/run, related prior ledgers as context only, outcome, acceptance source, user authority/endpoint, spec and candidate identities, current phase and next action, completed/pending/blocked work, artifact paths, decisions, validation evidence and unresolved findings. The subagent register records each returned agent identifier and canonical task name when exposed, configured role, assignment, allowed paths, model/effort and selection rationale, problem identity and reserved attempt allocation, status, last result and next action. A returned canonical `task_name`/`agent_name` is a valid coordination identifier when the runtime exposes no separate opaque agent ID; record that opaque ID as unavailable, not missing progress. Record actual returned identifiers immediately after spawning; never invent IDs or replace a failed worker's row. Give workers the ledger path for context, require progress/failure reports, and reserve ledger writes to the owner.

Update before dispatch (assignment/reservation), immediately after dispatch (returned IDs), on reassignment or meaningful progress/results, after each gate verdict/evaluated failure, before waiting, and before final response, interruption handoff, or stopping. Keep current summary concise while preserving failed-attempt and gate history. Tie evidence to exact artifact revisions; later edits invalidate affected evidence. Ledger-only bookkeeping does not invalidate an unchanged product candidate or require recursive validation.

On resume, read the ledger first, recover failure counts and reservations, and reconcile recorded workers with available runtime state and actual artifacts. IDs are coordination handles, not durable proof that a worker remains live. Preserve stale IDs/history and record replacement IDs when needed. Fresh validation still requires newly spawned validators. Unknown attempt history is a recovery gap, never zero. The aggregate three-failure stop applies only to evaluated solution attempts in the current prompt-to-resolution run, including any explicit additional authorization. A separate later comment-review request starts with zero failed attempts; reading comments and discovering or reporting defects are not failed solution attempts. Continuing an unfinished or stopped run retains its count.

## Acceptance and verification

1. All eight entry points explicitly require owner-maintained ledgers and link to a shipped procedure/template within their own plugin; neither plugin needs the other installed.
2. Templates cover the fields above, including actual returned subagent IDs or canonical handles with unavailable fields identified, progress, evidence identity, reservations, failed attempts and recovery; local paths, discovery/matching and sole-writer ownership transfer are explicit.
3. Update and resume instructions make dispatch, waits, results, gate changes, stale IDs and stop handling recoverable without inferring success from a worker handle or resetting failures within the same run.
4. `ask` continues to prohibit library persistence/research, while permitting only its separate operational ledger. Bootstrap works before declarations/library exist, and installation works without a project or writes to plugin caches.
5. No distributed instructions retain optional-only recovery recording or contradict mandatory ledger ownership. README and current governing spec guidance agree. Historical reports need not be rewritten.
6. Written spec receives fresh engineering-auditor validation before implementation. A different fresh engineering auditor reviews document acceptance, links, template usability, and bounded walkthroughs: trivial delivery without workers; shape-to-deliver reuse; read-only library answer; clean bootstrap; projectless installation; parallel worker reservations/results; interrupted work with stale IDs and two failures; third failure stopping; unavailable/forbidden persistence; runtime returning only canonical handles; two tasks finding the same outcome ledger with active ownership; transfer to another checkout.
7. Final validator runs every skill quick validator, then both plugin validators and the existing installer suites as prescribed by the repository README. No new executable behavior or tests are needed for this documentation change.

8. A separate later request to review comments on the same PR starts a new run with zero failures, even if earlier work recorded failures or the comments challenge its result. Reading three defect comments consumes no attempts. Resuming an interrupted run with two evaluated failures retains two; a third failed solution stops that run and a request merely to continue does not reset it.

## Constraints

Keep templates compact and avoid per-skill duplicate schemas. Preserve source/agent packaging rules, authorization boundaries, fresh validation, independent plugin use, and existing leaf roles. Do not change manifest versions or generated personal agents for a local unreleased change.
